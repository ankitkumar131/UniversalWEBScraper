System Overview
The goal is to build a resilient, scalable, and intelligent web scraping platform that can:

Navigate to any website
Automatically dismiss pop-ups, modals, cookie banners, and overlays
Bypass bot detection systems (Cloudflare, PerimeterX, Akamai, DataDome, hCaptcha, reCAPTCHA)
Handle pagination (click-based, URL-based, infinite scroll, "Load More" buttons)
Wait for dynamic content / loaders / AJAX calls to complete
Extract structured data regardless of site layout
Scale horizontally to scrape thousands of sites concurrently
Retry intelligently on failures
Store data in a queryable, normalized format

Core Design Principles
Principle	Description
Modularity	Every capability (popup handling, CAPTCHA solving, pagination) is a pluggable middleware module. Swap, disable, or add modules without touching core logic.
Resilience	Every operation assumes failure. Automatic retries, circuit breakers, fallback strategies (headless → headed, browser → API), and dead-letter queues.
Stealth-First	Every browser instance is hardened against detection by default. No request goes out without fingerprint randomization.
Domain-Aware Politeness	Per-domain rate limiting, robots.txt awareness, and configurable delays to avoid overloading targets.
Horizontal Scalability	Stateless workers pull from a shared queue. Scale by adding more worker containers.
Adaptive Intelligence	Use heuristics first, ML/LLM fallback second. The system learns common patterns (e.g., "Accept Cookies" button classes) and caches strategies per domain.
Observability	Every scrape job produces structured logs, metrics, and traces. You know exactly where and why something failed.
Tech Stack
Primary Recommendation
Layer	Technology	Why
Language	Python 3.11+ (primary) + Node.js (stealth plugins)	Python has the richest scraping ecosystem. Node.js needed for Puppeteer stealth plugins.
Browser Automation	Playwright (Python)	Supports Chromium, Firefox, WebKit. Better API than Selenium. Built-in auto-wait. Network interception.
Stealth Layer	playwright-stealth + puppeteer-extra-plugin-stealth (via Node bridge)	Patches all known bot detection vectors.
Cloudflare Bypass	undetected-chromedriver / Camoufox / FlareSolverr	Specialized tools to pass Cloudflare JS challenges.
CAPTCHA Solving	2Captcha API / Anti-Captcha / CapSolver	External CAPTCHA-solving services with human workers + AI.
Proxy Management	BrightData / Oxylabs / SmartProxy / Scrapingbee (residential + datacenter + mobile pools)	Residential proxies are essential for avoiding IP-based blocks.
Job Queue	Celery with Redis broker (or BullMQ if Node.js)	Distributed task queue with retries, priorities, rate limiting.
Task Scheduler	Celery Beat / APScheduler	Periodic re-scraping, cron-based triggers.
Orchestration	Docker + Kubernetes (or Docker Compose for small scale)	Containerized browser workers. Easy horizontal scaling.
API Layer	FastAPI	Async, fast, auto-documented API for submitting scrape jobs and retrieving results.
Structured Storage	PostgreSQL	Relational data, job tracking, extracted structured data.
Semi-Structured Storage	MongoDB	Flexible schemas for varied scraped data across different sites.
Raw Storage	S3 / MinIO	HTML snapshots, screenshots, PDFs, downloaded files.
Search	Elasticsearch / Meilisearch	Full-text search across scraped content.
Cache	Redis	Page cache, session cache, deduplication bloom filters, rate limiter state.
LLM Integration	OpenAI GPT-4o / Claude / local Llama via LangChain	Intelligent extraction when CSS selectors are unreliable. Schema-aware data extraction from arbitrary pages.
Monitoring	Prometheus + Grafana	Real-time dashboards: success rates, pages/min, proxy health.
Error Tracking	Sentry	Exception tracking with full context.
Logging	Structlog → Loki / ELK	Structured JSON logs for debugging and auditing.

Design Decisions:

Every scrape request is a Job with a unique ID, configuration, and lifecycle state.
Configuration includes: target URL, extraction schema, pagination strategy, proxy preference, priority level.
Jobs are idempotent — re-submitting the same job with the same config deduplicates or re-runs based on policy.

Anti-Detection & Bypass Layer
This is the most critical layer. Modern websites use sophisticated bot detection. Here's how each vector is handled:

Detection Vectors & Countermeasures
Detection Method	What They Check	Our Countermeasure
User-Agent	Browser version, OS	Rotate realistic UA strings from a curated database
Navigator properties	navigator.webdriver, navigator.plugins, navigator.languages	Playwright-stealth patches all properties
WebRTC leak	Real IP exposed via WebRTC	Disable WebRTC or proxy WebRTC traffic
Canvas fingerprint	Unique canvas rendering	Add subtle noise to canvas operations
WebGL fingerprint	GPU renderer strings	Spoof WebGL vendor/renderer
AudioContext	Audio processing fingerprint	Override AudioContext methods
TLS fingerprint (JA3/JA4)	TLS handshake pattern	Use curl_cffi or Camoufox for realistic TLS
HTTP/2 fingerprint	Frame ordering, settings	Use real browser (Playwright) not raw HTTP clients
Behavioral analysis	Mouse movement, scroll patterns, click timing	Inject human-like behavior: random delays, mouse curves, scroll events
IP reputation	Datacenter IP ranges	Use residential/mobile proxies
Rate patterns	Too many requests too fast	Per-domain rate limiting with random jitter
Cookie/Session	Missing expected cookies	Persist browser profiles and cookies across sessions
Honeypot links	Hidden links only bots click	Never click invisible elements (check display:none, visibility:hidden, opacity:0)
JavaScript challenges	Execute complex JS to prove browser	Use real browser engine (not HTTP-only clients)
Stealth Implementation Architecture
text

Stealth Module Pipeline:
│
├── 1. Browser Profile Generator
│   ├── Generate consistent fingerprint (screen res, timezone, locale, platform)
│   ├── Store profiles in DB for reuse per domain
│   └── Rotate profiles periodically
│
├── 2. Playwright Stealth Patches
│   ├── navigator.webdriver = undefined
│   ├── navigator.plugins = [realistic plugin array]
│   ├── navigator.languages = ["en-US", "en"]
│   ├── window.chrome = { runtime: {} }
│   ├── Permissions.query patch
│   └── iframe contentWindow patch
│
├── 3. Canvas/WebGL Noise Injection
│   ├── Override toDataURL() and toBlob() with subtle pixel noise
│   └── Spoof WebGL unmasked vendor/renderer
│
├── 4. Behavior Simulator
│   ├── Random mouse movements (Bézier curves, not linear)
│   ├── Random scroll events (variable speed)
│   ├── Realistic typing speed (variable delay between keystrokes)
│   ├── Random viewport focus/blur events
│   └── Random delays between actions (normal distribution: 500ms-3000ms)
│
├── 5. TLS Fingerprint Matching
│   ├── Use browser engine for all requests (not httpx/requests)
│   ├── For API-level scraping: curl_cffi with Chrome/Firefox impersonation
│   └── Camoufox for Firefox-based stealth
│
└── 6. Header Normalization
    ├── Send headers in correct browser order
    ├── Include realistic Accept, Accept-Language, Accept-Encoding
    ├── Include Sec-Fetch-* headers
    └── Never send bot-indicative headers
Pop-up & Overlay Handler
Strategy: Multi-Layer Detection & Dismissal
Pop-ups are handled through a priority-ordered pipeline of detection strategies:

text

Pop-up Handler Pipeline:
│
├── Layer 1: KNOWN PATTERN DATABASE
│   │
│   ├── Maintain a database of known pop-up selectors per domain
│   ├── Common patterns (works on 80%+ of sites):
│   │   ├── Cookie banners: #cookie-banner, .cookie-consent, #gdpr, .cc-banner
│   │   ├── Newsletter: .modal-newsletter, .popup-subscribe, #email-popup
│   │   ├── Age verification: .age-gate, #age-verify
│   │   ├── Notification: .notification-bar, .push-notification-prompt
│   │   └── Paywall soft: .paywall-overlay, .meter-wall
│   │
│   └── Action: Click known dismiss buttons:
│       ├── "Accept", "Accept All", "I Agree", "Got It", "Close", "✕", "×"
│       ├── button[class*="accept"], button[class*="agree"], button[class*="dismiss"]
│       └── [aria-label="Close"], [aria-label="Dismiss"]
│
├── Layer 2: GENERIC OVERLAY DETECTION
│   │
│   ├── Detect elements with:
│   │   ├── position: fixed + high z-index + covering viewport
│   │   ├── role="dialog" or role="alertdialog"
│   │   ├── class/id containing: modal, popup, overlay, banner, consent
│   │   └── Backdrop/overlay divs (semi-transparent full-screen divs)
│   │
│   └── Action:
│       ├── Find and click close/dismiss buttons within the overlay
│       ├── Press Escape key
│       ├── Click outside the modal (on backdrop)
│       └── If all else fails: hide via JavaScript (element.style.display = 'none')
│
├── Layer 3: MUTATION OBSERVER (for delayed pop-ups)
│   │
│   ├── Set up MutationObserver on document.body
│   ├── Watch for new nodes being added with modal/popup characteristics
│   ├── Trigger dismissal logic when detected
│   └── Handle pop-ups that appear after scroll, time delay, or interaction
│
├── Layer 4: CSS INJECTION (nuclear option)
│   │
│   ├── Inject CSS to force-hide common overlay patterns
│   ├── Remove overflow:hidden from body (sites lock scrolling behind modals)
│   └── Set pointer-events: auto on main content
│
├── Layer 5: BROWSER PERMISSIONS
│   │
│   ├── Auto-deny notification permission requests
│   ├── Auto-deny location permission requests
│   ├── Auto-deny camera/microphone requests
│   └── Block alert(), confirm(), prompt() dialogs
│
└── Layer 6: LLM VISUAL ANALYSIS (last resort)
    │
    ├── Take screenshot of the page
    ├── Send to vision LLM (GPT-4o, Claude)
    ├── Ask: "Identify any pop-ups, modals, or overlays blocking content. 
    │         What button should be clicked to dismiss them?"
    └── Execute the suggested action
Cloudflare & Bot Verification Bypass
Challenge Types & Solutions
text

Challenge Detection & Bypass:
│
├── 1. CHALLENGE DETECTOR
│   │
│   ├── Check response status codes:
│   │   ├── 403 → Potential block
│   │   ├── 503 → Cloudflare challenge page
│   │   └── 429 → Rate limited
│   │
│   ├── Check page content:
│   │   ├── "Just a moment..." → Cloudflare JS challenge
│   │   ├── "Checking your browser" → Cloudflare
│   │   ├── "Access denied" → WAF block
│   │   ├── "Please verify you are a human" → CAPTCHA challenge
│   │   ├── "Pardon our interruption" → DataDome
│   │   └── "Please enable JavaScript" → JS-required site
│   │
│   └── Check for challenge-specific elements:
│       ├── #cf-challenge-running → Cloudflare
│       ├── iframe[src*="hcaptcha"] → hCaptcha
│       ├── iframe[src*="recaptcha"] → reCAPTCHA
│       └── #px-captcha → PerimeterX
│
├── 2. JS CHALLENGE (Cloudflare "I'm Under Attack Mode")
│   │
│   ├── Strategy A: Wait it out (Playwright)
│   │   ├── Cloudflare JS challenges auto-solve in 3-5 seconds
│   │   ├── Use real browser engine with stealth patches
│   │   └── Wait for challenge to complete, then extract cf_clearance cookie
│   │
│   ├── Strategy B: FlareSolverr (dedicated service)
│   │   ├── Run FlareSolverr as a microservice
│   │   ├── It maintains browser sessions that solve CF challenges
│   │   └── Returns cookies and solved HTML
│   │
│   ├── Strategy C: curl_cffi with cf_clearance
│   │   ├── Solve challenge once with browser
│   │   ├── Extract cf_clearance cookie
│   │   └── Use curl_cffi with matching TLS fingerprint for subsequent requests
│   │
│   └── Strategy D: Camoufox
│       ├── Firefox-based anti-detect browser
│       └── Different TLS fingerprint from Chromium (harder to detect)
│
├── 3. CAPTCHA CHALLENGES
│   │
│   ├── hCaptcha:
│   │   ├── Detect iframe with hcaptcha.com
│   │   ├── Extract sitekey from data attribute
│   │   ├── Send to 2Captcha/Anti-Captcha API
│   │   ├── Receive solution token
│   │   └── Inject token and submit form
│   │
│   ├── reCAPTCHA v2:
│   │   ├── Same flow as hCaptcha
│   │   └── Click checkbox first; if image challenge appears, send to solver
│   │
│   ├── reCAPTCHA v3 (invisible):
│   │   ├── Score-based, no visual challenge
│   │   ├── Mitigation: realistic behavior simulation
│   │   ├── Use residential proxies
│   │   └── Maintain browser sessions with history
│   │
│   ├── Turnstile (Cloudflare):
│   │   ├── Newer, harder to bypass
│   │   ├── Use CapSolver or 2Captcha Turnstile support
│   │   └── Fallback: managed browser sessions
│   │
│   └── Custom CAPTCHAs:
│       ├── Screenshot the challenge

Pagination & Infinite Scroll Engine
text

Pagination Engine:
│
├── AUTO-DETECTION MODULE
│   │
│   ├── Analyze page for pagination indicators:
│   │   ├── <a> or <button> with text: "Next", "→", "»", ">", "Load More"
│   │   ├── Elements with class/id containing: "pagination", "pager", "page-nav"
│   │   ├── <nav> elements containing numbered links
│   │   ├── URL patterns: ?page=1, /page/1, &offset=0, &start=0, &p=1
│   │   ├── rel="next" link in <head>
│   │   └── Infinite scroll indicators (scroll event listeners, IntersectionObserver)
│   │
│   └── Classify pagination type:
│       ├── TYPE_A: Traditional numbered pagination
│       ├── TYPE_B: Next/Previous button only
│       ├── TYPE_C: URL-based pattern (increment number in URL)
│       ├── TYPE_D: Infinite scroll (content loads on scroll)
│       ├── TYPE_E: "Load More" button
│       ├── TYPE_F: AJAX/API-based (detect XHR/fetch calls returning data)
│       └── TYPE_G: Cursor-based / token-based (API pagination)
│
├── STRATEGY EXECUTION
│   │
│   ├── TYPE_A & TYPE_B: Click-based
│   │   ├── Find and click "Next" or page number
│   │   ├── Wait for page load / content update
│   │   ├── Detect if content actually changed (hash comparison)
│   │   └── Continue until: no next button, max pages reached, or duplicate content
│   │
│   ├── TYPE_C: URL-based
│   │   ├── Generate URLs from detected pattern
│   │   ├── Request each URL directly (can parallelize!)
│   │   └── Continue until: empty results or max pages
│   │
│   ├── TYPE_D: Infinite scroll
│   │   ├── Scroll to bottom of page
│   │   ├── Wait for new content to load (MutationObserver on content container)
│   │   ├── Count items before/after scroll to detect new items
│   │   ├── Continue scrolling until: no new items, max items reached, or spinner disappears permanently
│   │   └── Handle "scroll back up" patterns (some sites unload content)
│   │
│   ├── TYPE_E: Load More button
│   │   ├── Click the "Load More" button
│   │   ├── Wait for new items to appear
│   │   ├── Repeat until button disappears or max items reached
│   │   └── Some sites replace "Load More" with a spinner; wait for spinner to complete
│   │
│   └── TYPE_F & TYPE_G: API-based
│       ├── Intercept XHR/fetch calls during page load
│       ├── Identify the API endpoint returning list data
│       ├── Replay the API call with incremented page/offset/cursor parameters
│       ├── Parse JSON response directly (much faster than DOM parsing!)
│       └── Continue until: empty results array or cursor is null
│
├── DEDUPLICATION
│   │
│   ├── Hash each extracted item (based on unique fields)
│   ├── Maintain bloom filter or set of seen hashes
│   ├── Skip duplicate items
│   └── Detect when pagination loops back to page 1 (common on misconfigured sites)
│
├── TERMINATION CONDITIONS
│   │
│   ├── Max pages reached (configurable, default: 100)
│   ├── Max items reached (configurable)
│   ├── Max time elapsed (configurable, default: 30 minutes)
│   ├── Consecutive pages with no new items
│   ├── HTTP error on next page
│   └── Content hash unchanged after pagination action
│
└── OPTIMIZATION
    ├── Parallelize URL-based pagination (process 5 pages concurrently)
    ├── For API-based: bypass browser entirely, use httpx
    └── Progressive extraction: extract and save data per page (don't wait for all pages)
Data Extraction Pipeline
text

Extraction Engine:
│
├── MODE 1: SELECTOR-BASED (fastest, most reliable when selectors are known)
│   │
│   ├── CSS Selectors
│   ├── XPath expressions
│   ├── Compound selectors with fallbacks: [".price", ".cost", "[itemprop='price']"]
│   └── Attribute extraction: href, src, data-*, innerText, innerHTML
│
├── MODE 2: SCHEMA-BASED AUTO-DETECTION
│   │
│   ├── Detect structured data already on page:
│   │   ├── JSON-LD (<script type="application/ld+json">)
│   │   ├── Microdata (itemprop, itemscope)
│   │   ├── RDFa
│   │   ├── Open Graph meta tags
│   │   └── Twitter Card meta tags
│   │
│   └── Parse and normalize to unified schema
│
├── MODE 3: LLM-BASED INTELLIGENT EXTRACTION
│   │
│   ├── When to use:
│   │   ├── Unknown site structure
│   │   ├── Selectors change frequently
│   │   ├── Complex, unstructured content
│   │   └── When user provides natural language extraction instructions
│   │
│   ├── Implementation:
│   │   ├── Clean HTML (remove scripts, styles, nav, footer)
│   │   ├── Convert to markdown (reduce token count)
│   │   ├── Send to LLM with extraction prompt + output schema
│   │   ├── Parse structured JSON response
│   │   └── Validate against expected schema
│   │
│   └── Optimization:
│       ├── Cache extraction strategies per domain
│       ├── Use LLM to GENERATE selectors, then use selectors for subsequent pages
│       ├── Use smaller/local models (Llama 3, Mistral) for simple extraction
│       └── Chunk large pages to stay within context limits
│
├── MODE 4: HYBRID (recommended default)
│   │
│   ├── Try structured data extraction first (JSON-LD, microdata)
│   ├── Fall back to selector-based extraction
│   ├── Fall back to LLM-based extraction
│   └── Merge results from all sources, prefer structured data
│
├── MODE 5: API INTERCEPTION
│   │
│   ├── Monitor network requests during page load
│   ├── Identify API calls that return the data we need
│   ├── Extract data directly from API responses (JSON)
│   └── Often contains more data than what's rendered on page
│
└── POST-EXTRACTION PROCESSING
    ├── Type coercion (strings to numbers, dates to ISO format)
    ├── Text cleaning (trim, normalize whitespace, decode entities)
    ├── URL resolution (relative → absolute)
    ├── Image URL extraction and optional download
    └── Schema validation (ensure required fields are present)

│   │
│   └── Identity persistence:

│       ├── Reuse same identity with same proxy
│       └── Rotate identity when rotating proxy
│

    ├── Easy sites (no protection): datacenter proxy, or direct

Request Lifecycle (End-to-End Flow)
text

COMPLETE REQUEST LIFECYCLE:

1. JOB SUBMISSION
   │
   └─► API receives scrape request → validates config → creates Job record 
       in PostgreSQL → pushes to appropriate Celery queue

2. JOB PICKUP
   │
   └─► Celery worker picks job from queue → checks rate limiter for domain
       → if rate limited, re-queue with delay → if clear, proceed

3. RENDERING DECISION
   │
   ├─► Check domain difficulty score in Redis
   ├─► If score = "easy" → try lightweight (httpx + curl_cffi)
   ├─► If score = "medium" → use headless Playwright
   ├─► If score = "hard" → use Playwright + stealth + residential proxy
   └─► If unknown → start lightweight, escalate on failure

4. IDENTITY SETUP
   │
   ├─► Select proxy from appropriate pool
   ├─► Generate or retrieve matching identity profile
   ├─► Configure browser context with fingerprint
   └─► Set up network interception (for API detection)

5. PAGE LOADING
   │
   ├─► Navigate to target URL
   ├─► Wait for initial page load (network idle / DOM content loaded)
   ├─► Start timer for overall page readiness
   └─► Begin middleware pipeline

6. CHALLENGE DETECTION & SOLVING
   │
   ├─► Check if page is a Cloudflare/bot challenge page
   ├─► If JS challenge → wait for auto-solve (3-5 seconds)
   ├─► If CAPTCHA → detect type → send to solving service → inject solution
   ├─► If blocked → escalate (better proxy, different strategy)
   ├─► Extract and cache any clearance cookies
   └─► Verify we've reached the actual content page

7. OVERLAY DISMISSAL
   │
   ├─► Run cookie consent handler → accept/dismiss
   ├─► Run popup handler → dismiss modals, banners, notifications
   ├─► Block browser permission prompts
   ├─► Remove scroll locks (overflow: hidden on body)
   └─► Wait for any animations to complete

8. CONTENT READINESS
   │
   ├─► Wait for loaders/spinners to disappear
   ├─► Wait for skeleton screens to be replaced with content
   ├─► Wait for lazy-loaded images (if needed)
   ├─► Wait for custom readiness selector (if configured)
   └─► Verify content is present (not empty, not error page)

9. DATA EXTRACTION (FIRST PAGE)
   │
   ├─► Try structured data extraction (JSON-LD, microdata)
   ├─► Apply configured selectors (CSS/XPath)
   ├─► If no selectors configured → use LLM extraction
   ├─► If LLM used → cache generated selectors for subsequent pages
   ├─► Extract all matched items
   ├─► Store raw HTML snapshot to S3
   └─► Take screenshot (optional, for debugging)

10. PAGINATION
    │
    ├─► Auto-detect pagination type (if not configured)
    ├─► Execute pagination strategy (click next / scroll / change URL)
    ├─► Wait for new content to load
    ├─► Run overlay dismissal again (pop-ups may reappear)
    ├─► Extract data from new page
    ├─► Deduplicate against already-extracted items
    ├─► Check termination conditions
    └─► Repeat until done

11. DATA PROCESSING
    │
    ├─► Deduplicate extracted items
    ├─► Clean and normalize data (trim, type coerce, URL resolve)
    ├─► Validate against expected schema
    ├─► Enrich with metadata (source URL, timestamp, job ID)
    └─► Transform to output format

12. STORAGE
    │
    ├─► Save to primary store (PostgreSQL or MongoDB)
    ├─► Index in Elasticsearch (if search enabled)
    ├─► Save raw HTML/screenshots to S3
    └─► Update job status to "completed"

13. NOTIFICATION
    │
    ├─► Fire webhook (if configured)
    ├─► Update metrics (pages scraped, items extracted, duration)
    ├─► Update domain difficulty score based on outcome
    └─► Release browser context and proxy back to pools

14. ERROR HANDLING (at any step)
    │
    ├─► Capture error with full context
    ├─► Log structured error to logging system
    ├─► Report to Sentry
    ├─► If retryable → re-queue with backoff
    ├─► If escalatable → retry with higher-tier strategy
    ├─► If fatal → move to dead letter queue → update job as "failed"
    └─► Save partial results (if any pages were successfully scraped)
Failure Recovery & Retry Strategy
text

Retry & Recovery System:
│
├── RETRY CLASSIFICATION
│   │
│   ├── Transient errors (auto-retry):
│   │   ├── Network timeout
│   │   ├── Connection reset
│   │   ├── 502, 503, 504 HTTP errors
│   │   ├── Browser crash
│   │   ├── CAPTCHA solving timeout
│   │   └── Proxy connection failure
│   │
│   ├── Escalation errors (retry with different strategy):
│   │   ├── 403 Forbidden (escalate proxy tier)
│   │   ├── Cloudflare challenge (escalate to FlareSolverr)
│   │   ├── CAPTCHA failed (try different solving service)
│   │   └── Empty content (try different browser/rendering)
│   │
│   └── Fatal errors (no retry):
│       ├── 404 Not Found
│       ├── Invalid URL
│       ├── Domain doesn't exist
│       └── Max retries exhausted
│
├── RETRY POLICY
│   │
│   ├── Max retries: 3 (configurable per job)
│   ├── Backoff: exponential with jitter
│   │   ├── Retry 1: 5-10 seconds
│   │   ├── Retry 2: 15-30 seconds
│   │   └── Retry 3: 60-120 seconds
│   │
│   └── Strategy escalation on each retry:
│       ├── Retry 1: Same strategy, different proxy
│       ├── Retry 2: Higher-tier proxy + different browser
│       └── Retry 3: Full stealth + CAPTCHA solver + residential proxy
│
├── CHECKPOINT & RESUME
│   │
│   ├── Save pagination state after each page
│   ├── On failure mid-pagination: resume from last successful page
│   ├── Store partial results in database
│   └── Mark job as "partially_completed" if some pages succeeded
│
└── CIRCUIT BREAKER (per domain)
    │
    ├── Track failure rate per domain (sliding window)
    ├── If failure rate > 70% in last 10 requests → circuit OPEN
    ├── Circuit OPEN: pause all jobs for this domain for 5 minutes
    ├── After cooldown: allow 1 test request (circuit HALF-OPEN)
    ├── If test succeeds → circuit CLOSED, resume normal operation
    └── If test fails → circuit OPEN again, increase cooldown

Cost Centers:

Summary
This system design provides a production-grade, scalable web scraping platform that handles the full spectrum of modern web challenges. The key architectural decisions are:

Middleware pipeline architecture — each concern (stealth, popups, CAPTCHAs, pagination) is isolated and composable
Tiered rendering strategy — don't use expensive browser rendering when simple HTTP requests work
Adaptive difficulty scoring — the system learns which sites are hard and applies appropriate resources
LLM-augmented extraction — handles arbitrary sites without manual selector configuration
Resilient queue-based processing — failures are expected and handled gracefully with retries and escalation
Horizontal scalability — stateless workers behind a shared queue, scale with Kubernetes
The system is designed to scrape any website on the internet while being as stealthy, efficient, and resilient as possible.
